# V29 图片精准度自查

## 1. 复现问题

真实运行截图中，正文第二张图片是与“仓库管理员入库产生库存数据”段落无直接关系的 AI 汽车识别图；第三张则是媒体页面的公众号二维码。两者说明 V28 仍存在“全局主题得分压过局部段落语义”和“来源页 provenance 压过视觉卫生”的问题。

## 2. V29 处理顺序

1. 页面解析阶段先过滤 URL / alt / class/id 的二维码、扫码、公众号、微信、Logo、广告等信号；
2. 对实际下载图片执行本地 QR finder-pattern 检测，随机哈希 URL 也无法绕过；
3. 根首页不是具体新闻页，不享受 exact-source 旁路；
4. 当前段落出现明确业务场景时，生成该场景的短图片 Query；
5. Serper 泛图必须命中局部场景锚点，才进入最终排序。

## 3. 固定样例

段落：`仓库管理员做了一次入库，系统马上产生一条库存数据，并进入后续补货流程。`

V29 首选 Query：`仓库 库存管理 入库 数据采集`。

- 泛 AI 汽车识别候选：semantic anchor = False；
- 仓库/库存/入库候选：semantic anchor = True；
- 固定评分样例：前者约 9.3，后者约 33.3；最终门禁会在评分前直接拒绝前者。

## 4. 二维码测试

新增合成 QR finder-pattern 回归测试，同时加入普通黑白技术示意图反例，确保“拒绝二维码”不会粗暴演变成“拒绝所有黑白图”。还覆盖：

- URL 为随机哈希但像素是二维码；
- alt 为“扫码关注微信公众号”；
- 来源页二维码失败时，同一并行波次的 Serper 正常候选仍能成功接管；
- 媒体根首页不会被当作具体文章图片来源。

## 5. 成本

QR 检测发生在已经下载的候选上，本地执行且使用 Pillow；不新增 API、LLM、OCR。直方图判断先快速排除绝大多数普通照片，只有近方形高对比候选才进入 finder-pattern 扫描。搜索调用预算与 V28 相同。
